<a id="1"></a>
## 1. NP = «명사 + 선택적 수식어» — «선택적 수식어» 가 뭐야?

**NP(noun phrase, 명사구)** = 명사 하나를 중심으로 뭉친 말덩어리다. SAM3 논문 §2 (p3):

> *"We restrict concepts to those defined by **simple noun phrases (NPs) consisting of a noun and
> optional modifiers**."*

- **명사(head noun)** = 그 덩어리가 «무엇인가» 를 정하는 중심 낱말. **반드시 있어야 한다.**
  ⚠️ **«head noun» 은 논문 낱말이 아니다** — 논문은 그냥 `a noun` 이라 쓴다(→ §14).
- **수식어(modifier)** = 그 명사를 **좁히는** 말. **있어도 되고 없어도 된다** → 그래서 «선택적(optional)».

우리 프롬프트 `f002` 로 보면:

```
cube shaped   sealed   plastic   wafer   pod
└─ 수식어 ─┘  └수식어┘ └수식어┘  └수식어┘  └ 명사 ┘
   형상        상태     재질      용도     ← "이게 무엇인가"
```

★ **`pod` 이 «무엇인가» 를 정하고, 앞의 넷은 «어떤 pod 인가» 를 좁힌다.**
수식어를 다 떼고 `pod` 만 써도 NP 이고(그래서 «선택적»), 반대로 **명사를 빼면 NP 가 아니다.**

⚠️ 「선택적 = 있어도 되고 없어도 된다」는 **문법적으로** 그렇다는 뜻이지 **성능이 같다는 뜻이 아니다.**
실제로 수식어를 바꾸면 검출률이 크게 달라진다(§39 프롬프트 서열).

## 2. «형상어는 수식어 자리에서만 접지된다» 가 무슨 말이야?

**«접지(grounding)»** = 낱말을 **이미지 안의 실제 영역에 대응시키는 것**. *"이 낱말이 가리키는 게
사진 속 여기다"* 를 모델이 찾아내는 일이다.

우리가 측정한 것은 이 두 문장의 차이다:

| 프롬프트 | 구조 | 모델이 찾는 것 | 결과 |
|---|---|---|---|
| `cube shaped case` | 수식어 `cube shaped` + **명사 `case`** | **«상자» 인데 정육면체 모양인 것** | ✅ **9/9** |
| `plastic cube` | 수식어 `plastic` + **명사 `cube`** | 🔴 **«정육면체» 인데 플라스틱인 것** | ❌ **0/9** |

낱말은 `cube` 로 같은데 **자리가 다르다.**
- 앞 문장에서 `cube shaped` 는 **수식어** → «case 를 좁히는 조건» 으로 쓰인다.
- 뒤 문장에서 `cube` 는 **명사(head)** → «찾을 대상 그 자체» 가 된다.

FOUP 은 **«정육면체» 가 아니라 «정육면체처럼 생긴 통»** 이다. 그래서 `cube` 를 명사 자리에 놓으면
모델이 «진짜 정육면체(주사위·블록 같은 것)» 를 찾다가 아무것도 못 찾는다.

★ **정리: 형상을 나타내는 말은 «무엇인가» 자리(명사)에 놓으면 안 되고 «어떤가» 자리(수식어)에 놓아야
이미지에 붙는다.** 이게 «수식어 자리에서만 접지된다» 의 뜻이다.

🟡 **근거의 성격**: 관측(9/9 ↔ 0/9)은 🔴 **우리 측정**이고, «왜 그런가» 의 설명은 논문의
NP 구조 정의(§1)에서 우리가 끌어낸 해석이다 → §4 참조.

<a id="3"></a>
## 3. SA-Co 는 뭐야?

**SA-Co = Segment Anything with Concepts** — SAM3 를 만들면서 같이 구축한 **데이터셋 + 평가 벤치마크**다.
🟢 논문 초록:

> *"We open source SAM 3 along with our new **Segment Anything with Concepts (SA-Co) benchmark** for
> promptable concept segmentation."*

**규모** (🟢 논문 §1):

| | 규모 |
|---|---|
| 학습용 (사람 검수) | **4M** 개 고유 phrase · **52M** 개 마스크 |
| 학습용 (합성) | 38M phrase · 1.4B 마스크 |
| 벤치마크 | **207K** 개 고유 개념 · 이미지 120K · 영상 1.7K |

분할 이름이 여럿이다 — 학습 쪽은 `SA-Co/HQ`(고품질)·`SA-Co/SYN`(합성)·`SA-Co/EXT`,
평가 쪽은 `SA-Co/Gold`·`Silver`·`Bronze`·`Bio`·`VEval`·`VIDEO`.

**왜 우리 문서에 나오나** — 우리 경험 규칙 몇 개를 «이 데이터셋이 무엇으로 라벨링됐나» 로 설명하기
때문이다. 예: *"약어 `FOUP` 은 0/9 인데 `front opening unified pod` 은 9/9"* → **SA-Co 의 라벨이
«사람이 쓰는 NP 표층형» 이라 약어는 그 분포에 거의 없다**는 설명.

🔴 **주의 — «영어 전용» 은 논문에 그 문장이 있는 게 아니다.** 논문이 밝히는 것은 *"annotators were
proficient in English"* · *"minimum of B-2 English proficiency"*(§주석 정책)까지이고,
**«영어 NP 데이터셋»** 은 거기서 우리가 끌어낸 추론이다. 실제 증거는 **우리 측정**(한국어·일본어·독일어
프롬프트가 전부 0/9)이다. 보고서에는 *"측정 결과 영어 외 언어는 동작하지 않았고, 주석 정책상
영어 기반 데이터셋인 것과 정합적이다"* 로 쓴다.

## 4. SAM3 표의 «설계로부터의 설명» 은 논문에 근거한 설명인가?

**절반은 그렇고 절반은 우리 해석이다. 이 구분이 보고서에서 중요하다.**

> ✅ **2026-09-03 반영** — 이 질문 때문에 `CONFLUENCE_PIPELINE.md §3(나)` 표에 **«그렇게 해석한 근거»
> 열을 추가**했다. 아래는 그 열이 왜 필요한지에 대한 설명이고, **실제 근거는 그 표에 항목별로** 있다.

`CONFLUENCE_PIPELINE.md §3(나)` 의 표는 원래 **두 열**이었다:

| 열 | 무엇인가 | 근거 |
|---|---|---|
| **왼쪽 «측정된 규칙»** | *"`FOUP` 은 0/9, `front opening unified pod` 은 9/9"* | 🔴 **전부 우리 실험**. 논문에 없다 |
| **오른쪽 «설계로부터의 설명»** | *"SA-Co 는 NP 표층형으로 라벨링됐다"* | 🟡 **논문이 말한 «설계 사실» + 그 사실로 관측을 설명한 우리 추론** |

즉 **논문에 있는 것은 «설계» 이고, «그 설계가 이 관측을 설명한다» 는 우리 논증**이다.
논문 어디에도 *"약어를 쓰면 안 된다"* 같은 문장은 없다.

**설명마다 강도가 다르다** — 이렇게 나뉜다:

| 설명 | 강도 | 왜 |
|---|:-:|---|
| 색어가 틀리면 조용히 검출 0 ← **presence token** | 🟢 **강함** | 점수 분해식이 논문 §3 에 **수식으로** 있다(§7) |
| 형상어는 수식어 자리에서만 접지된다 ← **NP 구조** | 🟢 **강함** | NP = «명사 + 선택적 수식어» 가 논문 §2 의 **정의**다 |
| 핵명사를 빼면 검출이 깨진다 ← **head 가 개념을 정한다** | 🟡 중간 | 위와 같은 정의에서 따라 나오지만 논문이 그 실험을 한 건 아니다 |
| 슬롯별 최적의 조합이 최적이 아니다 ← **통째 임베딩** | 🟡 중간 | 텍스트 인코더가 phrase 단위인 것은 구조상 맞지만, «조합이 안 된다» 는 우리 관측이다 |
| 약어가 죽는다 ← **SA-Co 라벨 분포** | 🔴 **약함** | 데이터 분포를 우리가 직접 못 본다. **그럴듯한 설명**이지 확인된 원인이 아니다 |
| 영어 전용 ← **영어 NP 데이터셋** | 🔴 **약함** | §3 참조 |

★ **보고서 서술 원칙**: 왼쪽 열은 *"측정했다"*, 오른쪽 열은 *"논문이 밝힌 설계와 정합적이다"* 로 쓴다.
🔴 **«논문이 그렇게 말한다» 로 쓰면 안 되는 것**은 위 표에서 🔴 인 둘이다.

## 5. «head 가 개념을 정하고 modifier 는 좁힐 뿐» — modifier 가 뭐야?

§1 과 같은 이야기를 다른 각도에서 본 것이다.

- **head (핵명사)** = 명사구의 **중심 명사**. *"결국 이게 뭐냐"* 에 답한다. (🔴 논문 낱말이 아니다 → §14)
- **modifier (수식어)** = 그 head 를 **좁히는** 말. 형용사·분사·명사 모두 될 수 있다.

```
cube shaped sealed plastic wafer pod
                                └ head : "통(pod)이다"
└──────── modifier ────────┘     : "어떤 통이냐"를 좁힌다
```

**«좁힐 뿐» 이 무슨 뜻이냐면** — 수식어는 **후보 집합을 줄이지, 집합 자체를 바꾸지 않는다.**

| 프롬프트 | 모델이 보는 후보 집합 |
|---|---|
| `pod` | 세상의 모든 «pod» |
| `plastic pod` | 그중 **플라스틱인 것** ← 줄었다 |
| `sealed plastic pod` | 그중 **밀폐된 것** ← 더 줄었다 |
| 🔴 `cube` | **«정육면체» 전체** ← 집합이 **통째로 다른 것**으로 바뀌었다 |

★ **그래서 head 를 잘못 고르면 아무리 수식어를 붙여도 못 찾는다** — 처음부터 다른 집합을 뒤지기 때문이다.
반대로 head 만 맞으면 수식어가 좀 부실해도 «너무 많이 찾는» 문제로 끝난다(그건 §6 의 선택 규칙이 다룬다).

**우리 측정으로 확인된 것** — 핵명사를 빼면 **검출률 자체가 깨진다**(9/9 → 7/9). 반면 재질어는
`plastic`↔`polymer`↔`resin` 으로 바꿔도 나란히 잘 나온다. **head 가 훨씬 중요하다.**

<a id="6"></a>
## 6. «phrase 를 통째로 임베딩한다» — 임베딩이 뭐야?

**임베딩(embedding)** = **글자·낱말·문장을 숫자 벡터로 바꾼 것.**
신경망은 글자를 직접 못 다루므로, 텍스트를 «의미가 비슷하면 벡터도 가까운» 수백~수천 차원의 숫자
배열로 변환해서 넣는다.

```
"cube shaped sealed plastic wafer pod"
        ↓ 텍스트 인코더
[ 0.12, -0.44, 0.87, … ]   ← 길이 수백~수천의 숫자 배열 하나
```

**«통째로» 가 핵심이다** — 이 벡터는 **문장 전체에 대해 하나**가 나오지, 낱말마다 하나씩 나와서
더해지는 게 아니다. 그래서:

> 🔴 **문장의 성능을 «낱말별 점수의 합» 으로 분해할 수 없다.**

**우리가 실제로 겪은 결과** (규칙 ⑥):

| 슬롯별로 보면 | 그런데 조합하면 |
|---|---|
| `cube shaped` 는 `pod` 과 짝지을 때 **1위** | |
| `case` 는 다른 조합에서 괜찮았다 | 🔴 `cube shaped` + `case` 는 **꼴찌** |

★ **그래서 «좋은 낱말을 모아 최고 문장을 조립» 하는 접근이 통하지 않고, 문장을 통째로 시험해야 한다.**
136개를 낱개로 다 돌린 이유가 이것이다.

⚠️ 참고로 §7 의 presence token 점수도 **이 문장 벡터 하나에 대해** 계산된다 — 낱말별이 아니다.

<a id="7"></a>
## 7. presence token 이 뭐야?

SAM3 가 **«이 개념이 이 사진에 있기는 한가»** 를 따로 판단하려고 둔 **전용 슬롯(학습된 토큰)** 이다.

🟢 논문 §3 (p4) 원문:

> *"forcing proposal queries to understand the global context can be counterproductive, as it conflicts
> with the inherently local nature of the localization objective. **We decouple the recognition and
> localization steps by introducing a learned global presence token.** This token is solely responsible
> for predicting whether the target concept … **is present in the image/frame, i.e. p(NP is present in
> input)**. Each proposal query qᵢ only needs to solve the localization problem **p(qᵢ is a match | NP
> is present in input)**. **The final score … is the product of its own score and the presence score.**"*

**구조를 그림으로 풀면**

```
                     ┌── presence token ──→  p(개념이 이 사진에 있나)        ← 사진 전체에 하나
질의(프롬프트) ─────┤
                     └── proposal 여러 개 ──→ p(이 후보가 매치 | 개념이 있다면)  ← 후보마다 하나

              최종 score = (후보별 점수) × (presence 점수)
```

**왜 이렇게 나눴나** — «알아보기(recognition)» 와 «어디 있나(localization)» 는 성격이 다른 문제라,
후보 하나하나에게 «근데 이 개념이 사진에 있긴 하니?» 까지 판단시키면 오히려 나빠지기 때문이다.

**우리 파이프라인에 미치는 영향 둘**

1. 🔴 **색어가 틀리면 «조용히 검출 0» 이 되는 이유** — 몸체가 주황인데 `black …` 을 주면
   presence 항이 0 에 가까워지고, **곱셈이라 후보 점수가 아무리 높아도 최종 score 가 0 으로 눌린다.**
   ★ **버그가 아니라 설계된 동작**이다. 그래서 우리는 확정 프롬프트 4개에서 **색어를 전부 뺐다**.
2. ★ **`score` 로 순위를 매기면 안 되는 이유의 절반** — presence 항은 **사진 단위 상수**라 같은
   사진 안 후보들 사이에서는 **다 같이 곱해져 상쇄된다**. `score` 는 «품질» 지표가 아니라
   **«문턱(`--text-conf`)을 넘느냐» 지표**이므로 **중앙값이 아니라 최소값**(= 미검출까지의 여유)으로 읽는다.

## 8. spurious correlation 이 뭐야?

**«가짜 상관»** — 학습 데이터에서 **우연히 자주 같이 나타났다는 이유만으로** 모델이 배워 버린,
**인과관계가 아닌** 연관이다.

교과서적 예: 늑대 사진에는 대개 눈(snow)이 깔려 있어서, 모델이 «늑대» 대신 «흰 배경» 을 배운다.
눈밭의 개도 늑대라고 하고, 잔디밭의 늑대는 못 알아본다.

**우리 경우 — 제조사명** (규칙 ⑭):

프롬프트 `Entegris cube shaped sealed plastic wafer pod` 는
- 웹 사진 **9장** 실험에서 **1위**(score 0.988)였는데
- 웹 사진 **237장**으로 넓히니 **51위**로 떨어졌다.

🔴 **`Entegris` 라는 낱말이 «FOUP 이라는 물체» 가 아니라 «그 제조사 제품 사진의 특정 외관·색·로고»
와 결합해 있기 때문**이다. 9장이 마침 그 제조사 제품이라 잘 맞았고, 제조사가 섞이자 무너졌다.

★ **그래서 우리는 확정 프롬프트에서 제조사명을 뺐다.** 같은 이유로 색어도 뺐다 — 둘 다
**«물체의 정체» 가 아니라 «이 표본의 우연한 속성» 을 가리키는 말**이다.

⚠️ 이 함정은 **표본을 넓혀야만 보인다.** 9장에서 1위였던 것이 237장에서 51위가 된 것이
그 실례이고, 그래서 프롬프트 선정을 웹 237장 → 실물 3라운드로 넓혀 가며 좁혔다.

## 9. 코드는 `crop_ratio / 2` 인데 왜 1px 계산은 `/ 160` 이야?

**`/2` 는 «반지름», `×2` 는 «지름» 이라 서로 상쇄된다.** 계산을 끝까지 따라가면 이렇다.

**(1) 코드가 하는 일** (`Utils.py:605-622`)

```python
605:  radius  = mesh_diameter * crop_ratio / 2     # ① mm 단위 «반지름»
606:  offsets = [0,0,0,  radius,0,0,  -radius,0,0,  0,radius,0,  0,-radius,0]
611:  pts     = poses[:,:3,3] + offsets            # ② 물체 원점에서 ±radius 인 3D 점 4개
613:  uvs     = K @ pts                            # ③ 그 점들을 이미지에 투영
617:  radius  = max|uv - center|                   # ④ 픽셀 단위 반지름
618:  left  = center - radius                      # ⑤ 창의 왼쪽
619:  right = center + radius                      #    창의 오른쪽
597:  new_tf[0,0] = out_size[0] / (right - left)   # ⑥ 그 창을 160px 로 리샘플
```

**(2) 창의 «폭» 을 구해 보자**

⑤에서 `right − left = 2 × radius` 다. ①을 대입하면:

```
창의 폭 (mm) = 2 × radius = 2 × (mesh_diameter × crop_ratio / 2)
             = mesh_diameter × crop_ratio          ← /2 와 ×2 가 상쇄
```

**(3) 그 창이 160px 이 된다**

⑥에서 `out_size = 160`(🟢 논문 supplementary p14: *"resized into **160 × 160**"*). 따라서

```
네트워크 1px = 창의 폭 / 160
             = mesh_diameter × crop_ratio / 160   [mm]
```

★ **즉 `/2` 는 «중심에서 가장자리까지» 를 재려고 쓴 것이고, 창은 그 양쪽이라 폭이 2배가 되면서
사라진다.** 최종 식에는 `/2` 가 남지 않는다.

**(4) 우리 자산으로 숫자 넣기** (`crop_ratio` = refiner **1.2**)

| 메쉬 | `mesh_diameter` | 창의 폭 | ÷ 160 | = 네트워크 1px |
|---|--:|--:|--:|--:|
| `full.ply` | 579.0 mm | 579.0 × 1.2 = **694.8 mm** | ÷160 | **4.34 mm** |
| `top_flange.ply` | 183.5 mm | 183.5 × 1.2 = **220.2 mm** | ÷160 | **1.38 mm** |

→ **3.16배**(= 579.0 / 183.5). 이것이 stage2 의 이득이다.

⚠️ 부록 D 에 나오는 **«stage2 crop = 220mm»** 이 바로 이 표의 `220.2mm` 다 — 같은 값이다.

## 10. «거리에도 `fx` 에도 무관» 은 어떤 의미야?

**crop 을 «픽셀» 로 정하지 않고 «물체의 실제 크기(mm)» 로 정하기 때문에, 카메라를 옮겨도
네트워크가 보는 «1px 당 몇 mm» 가 변하지 않는다**는 뜻이다.

🟢 논문 §3.3 이 그렇게 설명한다:

> *"We then project the **slightly enlarged object diameter** … to determine the crop size."*

**두 방식을 비교하면 차이가 분명해진다**

| | 흔한 방식 — 고정 픽셀 crop | **FoundationPose — 3D 정의 crop** |
|---|---|---|
| 창을 정하는 기준 | *"검출 박스 주변 256×256 px"* | *"물체 지름 × 1.2 mm"* 를 투영한 만큼 |
| 물체가 **멀어지면** | 창 안에서 물체가 **작아진다** → 해상도 손해 | 창도 **같이 작아진다**(px 기준) → 물체가 차지하는 비율 **그대로** |
| `fx` 가 **커지면** | 물체가 **커진다** → 창 밖으로 나간다 | 창도 **같이 커진다** → 비율 **그대로** |
| **1px 당 mm** | `Z / fx` 에 비례해 **변한다** | 🔴 **`mesh_diameter × crop_ratio / 160` 로 고정** |

**왜 그렇게 되나** — ②~④에서 «물체 원점에서 ±radius mm 떨어진 3D 점» 을 **그때그때 투영해서**
창 크기를 정한다. 거리가 2배가 되면 그 점들의 투영 간격도 절반이 되므로 **창도 절반**이 된다.
그리고 어느 경우든 그 창을 **160px 로 리샘플**하므로, 창이 담는 **물리적 폭은 항상 같다.**

**우리 결론에 미치는 영향 — 두 가지**

1. ★ **`--primary full` 의 t 천장은 «거리로 못 낮춘다».** 카메라를 가까이 가져가도 네트워크가 보는
   1px 은 여전히 4.34mm 다. 실측이 이를 뒷받침한다 — 28→40→50cm 에서 t 가 2.87 → 2.20 → 2.41mm 로
   **거리와 함께 좋아지지 않는다**. **낮추는 유일한 방법은 메쉬를 바꾸는 것**(§4)이다.
2. ★ **`--input-scale` 로 입력을 줄여도 이 천장은 안 건드린다** — 배율은 원본 픽셀 수를 줄일 뿐,
   crop 은 3D 로 정의되므로 «1px 당 mm» 가 안 변한다(부록 B).

⚠️ **«무관» 은 «해상도가 무한하다» 가 아니다.** 거리가 멀어지면 원본에서 물체가 작아져 창을 160px 로
**늘리게(업샘플)** 되고, 그때는 없던 정보가 생기지 않는다. 정확히 말하면 **«mm/px 눈금이 거리에
따라 변하지 않는다»** 이지 «정확도가 거리와 무관하다» 가 아니다. 실제로 거리 사다리에서 ADD 는
0.29m 1.135mm → 0.85m 2.330mm 로 **단조 악화**한다.

## 11. `mesh_diameter` 579.0 / 183.5mm 는 CAD 메시에서 최대 직경을 잰 건가?

**맞다 — 메시 정점들 중 «가장 먼 두 점 사이의 거리» 다.** (`Utils.py:561-576`)

```python
561: def compute_mesh_diameter(model_pts=None, mesh=None, n_sample=1000):
572:     ids = np.random.choice(len(model_pts), size=min(n_sample, len(model_pts)))
573:     pts = model_pts[ids]                     # ← 정점 중 n_sample 개를 뽑고
574:     dists = np.linalg.norm(pts[None]-pts[:,None], axis=-1)
575:     diameter = dists.max()                   # ← 그중 최대 쌍거리
```

`estimater.py:54` 가 **`n_sample=10000`** 으로 부른다.

| 메쉬 | 무엇의 최대 쌍거리인가 | 값 |
|---|---|--:|
| `full.ply` | FOUP **전체**(몸체 + flange, 대각선) | **579.0 mm** |
| `top_flange.ply` | **top flange 만** (판의 대각선) | **183.5 mm** |

**🔴 주의할 점 셋**

1. **bbox 대각선이 아니다.** 표면 위 실제 두 점 사이 거리다.
   ⚠️ 옛 문서에 `656 / 203mm` 로 적혀 있던 적이 있는데 그건 **bounding box 대각선**이라 **다른 값**이다.
2. **난수가 섞인 값이다** — `np.random.choice` 로 정점을 뽑으므로 **실행마다 미세하게 다르다.**
   `n_sample` 기본값 1000 으로 재면 **560.6 / 183.1mm** 가 나온다(정점을 덜 뽑아 과소평가).
   ★ **인용할 때는 `n_sample=10000` 기준인 579.0 / 183.5 를 쓴다.**
3. **이 값이 정확도를 직접 정한다** — §9 의 1px 눈금과 §5(가)의 평행이동 보폭(`mesh_diameter/2`)
   **둘 다** 여기서 나온다. 그래서 «어느 `.ply` 를 넣느냐» 가 곧 «얼마나 세밀하게 보느냐» 다.

## 12. «refiner 1px» — refiner 가 뭐야?

FoundationPose 안에는 **학습된 신경망이 둘** 있고, 우리 코드가 그 둘을 만들어 넘긴다
(`pose_fp.py:292`: `scorer, refiner = ScorePredictor(), PoseRefinePredictor()`).

| | **refiner** (`PoseRefinePredictor`) | **scorer** (`ScorePredictor`) |
|---|---|---|
| 하는 일 | pose 하나를 받아 **«얼마나 어긋났나» 를 출력**해 고친다 | 여러 pose 후보를 **채점해 1등을 고른다** |
| 입력 | 「그 pose 로 CAD 를 렌더한 그림」 + 「같은 자리를 잘라낸 실제 관측」 | 같음 |
| 출력 | **`Δt`(평행이동 보정) + `ΔR`(회전 보정)** | 점수 하나 |
| `crop_ratio` | **1.2** | 1.1 |
| 입력 크기 | **160 × 160** | 160 × 160 |
| stage1 에서 | ✅ 쓴다 (240개 가설을 각각 정련) | ✅ 쓴다 (정련된 가설을 채점) |
| stage2 에서 | ✅ 쓴다 | 🔴 **안 쓴다** (§7.3) |

**«render-and-compare» 가 이 둘이 하는 일이다** — CAD 를 어떤 pose 로 렌더한 그림과 실제 사진을
나란히 놓고 *"얼마나 다른가"* 를 보고 pose 를 고친다. 그래서 **CAD 메시가 필수**다(§7.1).

★ **«refiner 1px» 은 «refiner 네트워크의 입력 이미지 1픽셀»** 이라는 뜻이다.
그 이미지가 **160×160** 이고 물체 지름 × 1.2 만큼의 영역을 담으므로 1px = 4.34mm(`full`) 다(§9).
**scorer 는 `crop_ratio` 가 1.1 이라 1px = 3.98mm** 로 살짝 다르지만, pose 를 실제로 «고치는» 것은
refiner 이므로 정밀도를 말할 때는 refiner 기준으로 인용한다.

⚠️ **두 네트워크는 가중치가 다르다** (`weights/2023-10-28-18-33-37` = refiner ·
`weights/2024-01-11-20-02-45` = scorer). 🟢 **우리는 둘 다 저자 배포본을 그대로 쓴다** — 재학습·미세조정 없음.
그리고 stage1·stage2 의 두 `FoundationPose` 인스턴스가 **이 네트워크 객체를 공유**한다
(`pose_fp.py:292`) — 즉 **바뀌는 것은 메시이지 가중치가 아니다.**

## 13. 형상어가 뭐야? (§2 를 다시)

🔴 **«형상어» 는 논문 용어가 아니라 우리가 만든 분류 이름**이다 — 프롬프트를 136개 만들어 서열화하면서
**«물체의 생김새를 말하는 낱말»** 을 한 묶음으로 부를 이름이 필요해서 붙였다.

**우리가 실제로 시험한 형상어 4종** (`RESULTS.md §39`):

| 형상어 | 예시 문장 | 웹 237장 서열 |
|---|---|---|
| **`cube shaped`** | `cube shaped sealed plastic wafer pod` | ★ **1위 계열** (사람 상위 13개 중 9개) |
| `boxy` | `boxy sealed plastic wafer pod` | 2위 계열 |
| `box shaped` | `box shaped sealed plastic wafer pod` | 대표 1개 |
| `blocky` | `blocky silicon plastic wafer case` | 🔴 하위 |

즉 **형상어 = `cube shaped` · `boxy` · `box shaped` · `blocky` 같은 «모양을 말하는 낱말»** 이다.
`plastic`(재질) · `sealed`(상태) · `wafer`(용도) 와 구분하려고 이름을 따로 붙였다.

**§2 가 말하는 것을 한 줄로 다시 쓰면**

> 🔴 **모양을 말하는 낱말은 «수식어» 로 써야 하고, 그 낱말을 «명사» 자리에 놓으면 안 된다.**

```
✅ cube shaped case     →  명사 = case  (통)          "정육면체 모양의 통을 찾아라"   9/9
❌ plastic cube         →  명사 = cube  (정육면체)     "플라스틱으로 된 정육면체를 찾아라"  0/9
```

**왜 뒤쪽이 실패하나** — FOUP 은 **«정육면체» 가 아니다.** 정육면체«처럼 생긴» 통이다.
`cube` 를 명사 자리에 놓으면 모델은 진짜 정육면체(주사위·나무 블록·큐브 퍼즐)를 찾으러 가고,
사진에 그런 게 없으니 아무것도 못 찾는다. 반면 `case`(통)를 명사로 두면 «통» 중에서 찾고,
`cube shaped` 는 그중 «정육면체처럼 생긴 것» 으로 **범위를 좁히는 역할**만 한다.

★ **기억할 한 문장**: *"찾을 대상은 **통**이지 **정육면체**가 아니다. 모양은 «어떤 통이냐» 를
말할 때만 쓴다."*

⚠️ **«접지(grounding)»** 는 «그 낱말이 사진 속 어디를 가리키는지 모델이 찾아내는 것» 이다.
그러니 *"형상어는 수식어 자리에서만 접지된다"* = *"모양 낱말은 수식어로 쓸 때만 사진에 제대로 붙는다"*.

## 14. head / modifier 는 논문에 나오는 개념인가?

**절반이다 — 개념은 논문 것이고, «head» 라는 낱말은 우리가 붙였다.** 원문을 세어 봤다:

| 낱말 | SAM3 논문(v2) 전문 등장 횟수 |
|---|:-:|
| `noun phrase` | **85회** |
| `modifier` | **1회** (아래 정의 문장에서만) |
| 🔴 `head noun` / `head-noun` | **0회** |

🟢 논문에 있는 문장은 이것 하나다 (§2, p3):

> *"We restrict concepts to those defined by simple noun phrases (NPs) **consisting of a noun and
> optional modifiers**."*

즉 논문의 용어는 **«noun(명사) + optional modifiers(선택적 수식어)»** 다.
**`modifier` 는 논문 낱말이 맞고**, **`head`(핵명사)는 언어학의 표준 용어를 우리가 가져다 쓴 것**이다.
가리키는 대상은 논문의 `a noun` 과 **완전히 같다**.

★ **보고서 서술 원칙**: *"논문은 NP 를 «명사 + 선택적 수식어» 로 제한한다"* 까지가 인용이고,
*"head 를 틀리면 못 찾는다"* 는 **그 정의에서 우리가 끌어낸 해석 + 우리 측정**이다(§4 참조).
🔴 **«논문이 head noun 이라 부른다» 로 쓰면 안 된다.**

## 15. «상표는 특정 외관과 결합한 spurious correlation» 이 무슨 뜻이야?

§8 의 정의를 제조사명에 구체적으로 적용한 문장이다. 풀어 쓰면 이렇다.

**(1) 모델이 낱말과 이미지를 어떻게 잇나** — SAM3 는 «낱말 ↔ 그 낱말이 붙은 이미지 영역» 짝을
대량으로 보고 배운다(학습 **4M** 개 고유 NP). 그런데 **왜 그 낱말인지는 안 가르쳐 준다.**
사진에 «그 낱말이 붙어 있다» 는 사실만 준다.

**(2) 그래서 상표는 «물체» 가 아니라 «그 회사 제품의 생김새» 를 배운다**

`Entegris` 라는 낱말이 붙은 학습 사진들은 전부 **한 회사 제품**이다. 그 사진들이 공유하는 것은:

| 진짜 배웠으면 하는 것 | 실제로 같이 배워 버리는 것 |
|---|---|
| «웨이퍼를 담는 통» | 그 회사 특유의 **색·로고 위치·손잡이 모양·문 디자인** |

모델 입장에서는 **둘을 구분할 방법이 없다.** 학습 데이터 안에서는 **항상 같이 나타났기 때문**이다.
이렇게 «원인이 아닌데 항상 같이 나타나서 배워 버린 연관» 이 **spurious correlation(가짜 상관)** 이다.

**(3) 우리 실험이 그것을 그대로 보여 준다**

| 표본 | `Entegris cube shaped sealed plastic wafer pod` 의 순위 |
|---|---|
| 웹 사진 **9장** (마침 그 제조사 제품) | ★ **1위** (score 0.988) |
| 웹 사진 **237장** (제조사 섞임) | 🔴 **51위** |

→ **9장에서는 «가짜 상관» 이 맞아떨어져서 오히려 1등**이었고, 제조사가 섞이자 무너졌다.

★ **그래서 «270K/4M 개념이라도» 라는 단서가 붙어 있다** — *"모델이 아무리 많은 개념을 알아도,
상표라는 낱말 자체가 «그 회사 외관» 과 묶여 있으니 개념 수로 해결되는 문제가 아니다"* 는 뜻이다.
개념을 더 많이 배울수록 **상표와 외관의 결합도 같이 강해진다.**

⚠️ **숫자 주의** — SA-Co 벤치마크 규모를 **저장소 README 는 «270K unique concepts»**,
**논문 v2 는 «207K»** 로 적는다. 출처가 어긋나므로 인용할 때 어느 쪽인지 밝힌다.
그리고 이 논증에 정말 필요한 숫자는 벤치마크가 아니라 **학습 개념 수(4M NP)** 다.

**(4) 같은 함정이 색어에도 있다** — `black …` 은 «검정 FOUP» 사진에서만 맞는데, 우리 실물 개체는
검정·주황·투명 셋이다. 그래서 확정 프롬프트 4개에서 **제조사명과 색어를 둘 다 뺐다.**

🔴 **일반 교훈**: *«이 표본에서 잘 되는 낱말» 과 «이 물체를 가리키는 낱말» 은 다르다.*
구분하는 유일한 방법은 **표본을 넓히는 것**이고, 실제로 9장 → 237장에서 순위가 50계단 무너졌다.

## 16. 🔴 `full` 만 쓰면 정확도가 절대 4.34mm 보다 작게 못 나오나?

**아니다 — 하한이 아니다.** 실측이 그것보다 **작다.**

**(1) 실측** (8거리 사다리 · 오선택 제외 · `--primary full` 의 stage1 출력 = `coarse`)

| 거리(m) | `coarse` t 중앙 | ÷ 4.34mm |
|---|--:|--:|
| 0.291 | 3.249 mm | **0.75 px** |
| 0.393 | 2.368 | **0.55 px** |
| 0.443 | 2.506 | 0.58 px |
| 0.491 | 2.341 | **0.54 px** |
| 0.548 | 2.518 | 0.58 px |
| 0.597 | 2.500 | 0.58 px |
| 0.697 | 2.558 | 0.59 px |
| 0.850 | 2.980 | 0.69 px |

→ **전 거리에서 0.54~0.75 px**, 중앙 **0.58 px**. **항상 1px 보다 작다.**

**(2) 왜 서브픽셀이 가능한가** — 네트워크가 내놓는 것은 **«몇 번째 픽셀» 이 아니라 연속값**이다.
`predict_pose_refine.py:199·229` 에서 `trans_delta` 는 실수 회귀값이고 거기에 `mesh_diameter/2` 를
곱한다. **정수 픽셀로 양자화되는 단계가 없다.** 게다가 160×160 = 25,600 픽셀을 함께 보고
5회 반복하므로 평균화 효과도 있다.

**(3) 그러면 4.34mm 는 뭔가 — «하한» 이 아니라 «눈금(scale)» 이다**

- 오차의 **크기를 정하는 단위**다. 실제 오차가 그 **0.6배 근처에 머문다.**
- 🔴 **핵심은 «거리로 안 내려간다» 는 것**이다 — 0.29m ↔ 0.85m 로 **2.9배 멀어져도** t 가
  2.34 → 2.98mm 로 **변화폭 0.91mm** 뿐이다. 카메라를 아무리 당겨도 이 대역을 못 벗어난다.
- ⚠️ 그래서 문서의 **«구조적 천장»** 은 *"이보다 큰 오차가 난다"* 가 아니라
  ***"이 대역 아래로 못 내려간다"*** 는 뜻이다. **«바닥» 이라 읽는 편이 정확하다.**

**(4) 내리는 방법은 하나 — 눈금을 바꾼다 (= 메시 교체)**

| 메시 | 1px 눈금 | 실측 t 중앙 | 몇 px 인가 |
|---|--:|--:|--:|
| `full.ply` (stage1) | 4.34 mm | 2.34~3.25 mm | 0.54~0.75 px |
| `top_flange.ply` (stage2) | **1.38 mm** | **0.71~2.15 mm** | 0.52~1.56 px |

★ 0.291m 에서 **0.714mm** — `full` 로는 어느 거리에서도 못 낸 값이다. 이것이 §4(메시 교체)의 이득이다.

🔴 **단 flange 쪽은 «px 비율» 이 거리에 따라 커진다**(0.52 → 1.56 px). 눈금은 거리 무관이지만
**다른 오차원(depth 잡음·투영 크기)이 멀어질수록 지배**하기 때문이다.
→ **«0.5px 는 상수가 아니다»**. `full` 쪽이 평평한 것은 이미 그 다른 오차원과 비슷한 크기여서다.

**(5) 그래서 요약**

| 질문 | 답 |
|---|---|
| 4.34mm 보다 작게 나오나? | ✅ **나온다** — 실측 2.34~3.25mm (0.54~0.75px) |
| 그럼 얼마까지 내려가나? | 🔴 **약 0.55px = 2.3mm 근처가 바닥**이고, **거리로는 못 내린다** |
| 더 내리려면? | **메시를 `top_flange.ply` 로 바꾼다** → 눈금 1.38mm, 실측 0.71mm(근거리) |
| KPI 대비 여유는? | `full` 단독 2.5mm 도 **KPI 5mm 의 50%** 라 이미 안쪽이다 |

## 부록. 한 장 요약 — 용어만

| 용어 | 한 줄 |
|---|---|
| **NP (noun phrase)** | 명사 하나를 중심으로 뭉친 말덩어리. SAM3 가 받는 프롬프트의 형식 |
| **head (핵명사)** | NP 의 중심 명사. *"결국 뭐냐"* 를 정한다. **빼면 안 된다** |
| **modifier (수식어)** | head 를 좁히는 말. 문법적으로 «선택적» |
| **접지 (grounding)** | 낱말을 이미지 속 실제 영역에 대응시키는 것 |
| **임베딩 (embedding)** | 텍스트를 숫자 벡터로 바꾼 것. **문장 단위로 하나** |
| **SA-Co** | *Segment Anything with Concepts* — SAM3 의 데이터셋 + 벤치마크 |
| **presence token** | *"이 개념이 사진에 있나"* 를 따로 판단하는 SAM3 의 전용 슬롯. 최종 점수에 **곱해진다** |
| **spurious correlation** | 우연히 같이 나타나서 배운 «가짜 상관». 제조사명·색어가 그 예 |
| **refiner** | pose 를 «고치는» 네트워크. 160×160 crop 을 본다 |
| **scorer** | pose 후보를 «채점하는» 네트워크. stage2 에서는 안 쓴다 |
| **`mesh_diameter`** | 메시 정점 중 가장 먼 두 점 사이 거리. 1px 눈금과 보폭을 **둘 다** 정한다 |
| **crop / `crop_ratio`** | 네트워크에 넣을 창. **3D(mm)로 정의**되고 160px 로 리샘플된다 |
